# Base de Datos - QuantumApp

Motor actual: **PostgreSQL** — Base de datos: `QuantumSystemDB` (local, puerto 5432, owner `postgres`)

> **Estado de la migracion**: la base se migro de MySQL `quantumappdb` a PostgreSQL `QuantumSystemDB` de manera **local** (septiembre 2026) y el **backend ya consume esta base de datos** (driver `pg`, capa `src/DB/pg.ts`). Los campos vectoriales estan poblados con embeddings de Gemini (`pgvector`). Pendiente: subir a Supabase y conectar el backend en Render (ver seccion 6 de `docs/Decisiones-tecnicas.md`).

## Diagrama de relaciones

```
Roles (1) ──── (N) Usuarios
                          │
              ┌───────────┴───────────┐
              │                       │
      Usuarios_Reservas       Usuarios_Vehiculos
              │                       │
              ▼                       ▼
          Reservas               Vehiculos
              │                       │
              │  color (FK)           │  id_color (FK, N:1, color principal)
              ▼                       ▼
      Colores ◄────── Vehiculos_Colores (N:M, ON DELETE CASCADE) ────► Vehiculos
                          (id_vehiculo, id_color)
```

- **Varios colores por modelo**: un modelo se ofrece en varios colores via la tabla N:M `Vehiculos_Colores` (tambien permite que un color este en varios modelos). La columna `Vehiculos.id_color` es el color **principal**.
- Tablas `Estaciones_Carga` y `Servicios_Tecnicos` son independientes (sin FKs).

## Extension y campos vectoriales

- Se instalo la extension **`vector` (pgvector)** a nivel de sistema (binarios compilados para PostgreSQL 17 en Windows: `vector.dll`, `vector.control`, scripts SQL; se reinicio el servicio `postgresql-x64-17`).
- Activacion por base: `CREATE EXTENSION IF NOT EXISTS vector;`.
- Las tablas **Usuarios, Vehiculos, Reservas, Servicios_Tecnicos y Estaciones_Carga** tienen una columna `"embedding" vector(768)` poblada con **embeddings semánticos de Google Gemini** (`gemini-embedding-001`, 768 dimensiones recomendada).
- Para buscar por similitud: `ORDER BY "embedding" <=> '<vector>'::vector` (coseno). Para vectores rapidos se puede crear `CREATE INDEX ... USING hnsw ("embedding" vector_cosine_ops)`.
- **Que guarda y para que sirve la columna**: hay **un vector por fila** (1 peticion a Gemini por fila; cada vector se guarda en la fila que le corresponde, con `UPDATE ... WHERE pk = <fila>`). Cada vector es la representacion **semantica del contenido de las demas columnas de esa fila** (el texto `"columna:valor ..."` es lo que Gemini convierte en vector). Su unico objetivo es servir de **clave de busqueda semantica**: cuando llega una pregunta, se la vectoriza con el mismo modelo y `<=>` compara ese vector contra los guardados para hallar que filas "hablan del mismo tema"; el **vector de la pregunta es solo la llave de busqueda y nunca se le pasa a la IA** (a la IA se le entrega el texto de la fila encontrada, no el vector).

## Como se reprodujo / vectorizacion

> Los scripts `QuantumSystemDB_postgres.sql` y `install_pgvector_pg17.{ps1,bat}` se eliminaron (eran herramientas puntuales de la migracion, no necesarias para el funcionamiento del backend). El esquema completo esta documentado en este archivo (seccion "Tablas") y la extension `vector` ya esta instalada en el sistema.

- **Vectorizador**: `Backend/scripts/vectorizar_datos.ts` — por cada fila arma el texto `"columna:valor ..."`, llama a la API de Gemini y guarda el vector en `"embedding"`. Lee la clave de `Backend/.env` (variable `API_KEY_GOOGLE_AI_STUDIO` o `GEMINI_API_KEY`). Si no hay clave usa un fallback local (feature hashing, sin IA). Conexion por `PGHOST/PGUSER/PGPASSWORD/PGDATABASE` (la contrasena se pasa por la variable `PGPASSWORD`).
  ```
  cd Backend/scripts && set PGPASSWORD=<clave_postgres> && npx ts-node vectorizar_datos.ts
  ```

## Notas de la migracion MySQL -> Postgres

- **Las relaciones (FKs) son las mismas que en la antigua base MySQL `quantumappdb`**: la migracion preservo el esquema de relaciones sin cambios. Verificado contra la base real `QuantumSystemDB` (FKs existentes: `Usuarios.id_rol -> Roles`, `Reservas.color -> Colores`, `Vehiculos.id_color -> Colores`, `Vehiculos_Colores` N:M con `ON DELETE CASCADE` en ambas FKs, `Usuarios_Reservas` y `Usuarios_Vehiculos` N:M; `Estaciones_Carga` y `Servicios_Tecnicos` siguen sin FKs).

---

- Los IDs se cargaron explicitos y se sincronizaron las secuencias con `setval(pg_get_serial_sequence('"Tabla"', 'id_campo'), ...)` — es obligatorio pasar el nombre de tabla **entre comillas dentro de la cadena** (`'"Tabla"'`) por los nombres mixtos; si no, PG lo resuelve en minusculas y falla.
- PostgreSQL es estricto con `VARCHAR(n)`: textos mas largos que el limite (caso de `horarios`) abortan la transaccion. Se ampliaron `horarios` (200), `direccion` (100) y `telefono` (30) en `Servicios_Tecnicos` y `Estaciones_Carga`.

## Flujo de vectorizacion (metodo estandar, actual)

Desde que existe `Backend/src/embeddings/`, **el propio backend vectoriza en tiempo real**: cada POST/PUT de `Usuarios`, `Vehiculos`, `Reservas`, `Servicios_Tecnicos` y `Estaciones_Carga` calcula el embedding de la fila (Gemini, o fallback local sin clave) y lo guarda en la columna `embedding` al mismo tiempo que inserta/actualiza. El script describe abajo queda como **respaldo/reproceso** para filas que quedaron con `embedding` en NULL (p. ej. la migracion inicial).

El script `Backend/scripts/vectorizar_datos.ts` es el **orquestador** entre la base y Gemini. El servicio de Gemini solo transforma texto en vector; **no lee ni guarda en la base de datos** — eso lo hace el script. Pasos:

1. Se conecta a `QuantumSystemDB` (usa `PGPASSWORD` y demas variables `PG*`).
2. Consulta las columnas reales de cada tabla (excluyendo `embedding`) y lee **solo las filas cuyo `embedding` es `NULL`** (`WHERE "embedding" IS NULL`); las ya vectorizadas se omiten.
3. Arma un texto por fila concatenando los campos: `"columna:valor columna:valor ..."` (p. ej. `Nombre_Modelo:KAIYI EQUTE Tipo:Auto Autonomia:300 km ...`); si supera 8000 caracteres lo recorta.
4. Envia ese texto a **Gemini** (`POST .../models/gemini-embedding-001:embedContent?key=<API_KEY>`, con `outputDimensionality: 768`).
5. **Gemini lo transforma en un vector** de 768 numeros y lo devuelve en la respuesta.
6. El script **recibe ese vector** y lo **guarda** en el campo `embedding` de la fila correspondiente (`UPDATE ... SET "embedding" = '<vector>'::vector WHERE "id" = ...`).
7. Repite por cada fila de cada tabla (con un retardo de 120 ms para el free tier).

> Omite las filas ya vectorizadas (`embedding IS NULL`), asi que es **incremental**: tras agregar una reserva (u otra fila) basta con reejecutar `npx ts-node vectorizar_datos.ts` y solo procesara la fila nueva. Para **recalcular** todos los vectores habria que borrar los `embedding` antes. Es determinista si se usa el mismo modelo. Sin clave (`API_KEY_GOOGLE_AI_STUDIO` en `Backend/.env`) el script cae a un fallback local (feature hashing, sin IA).

## Flujo del chatbot (RAG, pendiente de implementar)

Mas adelante el backend hara algo **parecido pero al reves** para responder preguntas del usuario:

1. El usuario escribe una pregunta en el frontend (chatbot).
2. El backend **vectoriza la pregunta** con el **mismo modelo** de Gemini.
3. Busca en Postgres las filas mas parecidas: `SELECT ... FROM "<Tabla>" ORDER BY "embedding" <=> '<vector_pregunta>'::vector LIMIT k` (operador coseno de pgvector; opcional: indice HNSW). El vector de la pregunta solo sirve de **llave de busqueda**: se compara contra los vectores guardados por fila en `embedding`.
4. Toma esas filas y extrae **su texto** (`"columna:valor ..."`); ese texto (no el vector) es el **contexto** que se le pasa a Gemini (modelo de texto) junto con la pregunta.
5. Gemini responde basandose en ese contexto y el backend entrega la respuesta **al frontend** (ida y vuelta: BD → IA → frontend). El vector guardado en BD permite **encontrar** que filas son relevantes, pero la IA solo ve texto.

## Migracion del backend a PostgreSQL (hecha)

El backend se migro de MySQL a PostgreSQL **conservando la arquitectura de capa DB por inyeccion** (septiembre 2026):

1. **Nueva capa `Backend/src/DB/pg.ts`** con la **misma interfaz** que tenia `src/DB/mysql.ts` (`todos`, `uno`, `agregar`, `actualizar`, `eliminar`, `query`, `ejecutar`), pero usando el driver `pg` (pool):
   - Identificadores con nombres mixtos entre **comillas dobles** (`FROM "Vehiculos"`, `"Nombre_Modelo"`).
   - Parametros `?` → `$1, $2...`; los `??` de las queries en crudo se convierten en identificadores entre comillas.
   - `INSERT ... ON CONFLICT DO NOTHING` (equivalente al upsert `ON DUPLICATE KEY UPDATE` de MySQL) y se ignoran los valores `undefined` al construir inserts/updates.
   - El tipo `DATE` se devuelve como texto `YYYY-MM-DD` (igual que devolvia MySQL).
2. **`Backend/src/config.ts`** ahora expone `config.pg` (host, user, password, database, port), leido de `PGHOST`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`, `PGPORT`.
3. **`Backend/.env`** se actualizo con la conexion local: `PGHOST=localhost`, `PGUSER=postgres`, `PGPASSWORD=123456`, `PGDATABASE=QuantumSystemDB`, `PGPORT=5432`.
4. **Se elimino** `Backend/src/DB/mysql.ts` (quedo sin uso) y se agrego `@types/pg` al backend.
5. **SQL en crudo ajustado a Postgres**: el JOIN de login (`auth/controlador.ts`) y las queries de colores de vehiculos (`Vehiculos/controlador.ts`) ahora citan los identificadores mixtos.
6. **`modulos/Clientes`** ahora apunta a la tabla `"Roles"` (PK `id_rol`) y sus firmas `uno`/`eliminar`/`agregar` quedaron consistentes con el resto de modulos (antes llamaban mal a la capa DB y a la tabla `roles`).

El sobre de respuesta, los modulos, las rutas y el flujo de peticiones **no cambiaron** (misma arquitectura).
